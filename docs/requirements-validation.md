# 人間関係管理ツール群：要求の妥当性検証

作成日: 2026-10-12 / 対象: https://github.com/hardlitchi/HumanRelationEmurator

## 0. 現状

リポジトリは空（コミットなし）。既存の設計・コード上の制約はないため、データ設計から始める判断は妥当。

## 1. 結論

**要求は妥当。** ただし、データ設計に入る前に「何をノード/エッジ/属性に置くか」と「誰の視点の情報か」を決めておかないと、後から構造を作り直すことになる。下記の曖昧点を4つの質問（§6）に絞った。

妥当と判断した根拠:

- 関係性をグラフで表すのは社会ネットワーク分析（SNA）で確立した方法。「親しさ＝信号の強さ」は Granovetter の *tie strength*（接触頻度・時間・感情的強度・互恵性）、「密度でクラスタが分かる」はクラスタ係数やコミュニティ検出（Louvain 等）にそのまま対応する。
- 「ノードごとにその人の情報を持つ」はプロパティグラフ（Neo4j 等）の標準的な形。
- 「マスターでフィールド名の揺れを防ぐ」は、AIエージェントが書き込む前提では特に重要。LLM は `birthday` / `birth_date` / `誕生日` を平気で混在させるため、これは要求の中で最も価値の高い部分だと考える。

## 2. 曖昧な点と、設計への影響

### 2.1 「信号の強度」を何で決めるか
- 手入力の数値（例: 親密度 1〜5）なのか、やり取りの記録（頻度・直近性・双方向性・継続期間）から算出するのか。
- **推奨:** やり取り（Interaction）をイベントとして記録し、強度はそこから算出する派生値にする。手入力の主観評価は別フィールドとして並存させる。数値だけ保存すると「なぜその強さなのか」が後から追えない。

### 2.2 「予測可能なコンテキスト」はノードではなくエッジに属する
- 「親しいと短いやり取りでも通じる」のは、その**2人の間で共有された文脈**（共通の経験・内輪の言葉・過去の話題）があるから。これは個人ノードの属性ではなく、関係（エッジ）側の属性。
- **推奨:** エッジにもコンテキスト（カスタムフィールド）を持たせる。マスターの各フィールドに「人に付く / 関係に付く / 組織に付く」の適用対象を持たせる。

### 2.3 密度と強度は別の量
- 強度は1本のエッジの重み、密度は部分グラフ全体の性質、共通の知人の数（埋め込み度）はその中間。相関はするが一致しない（弱い紐帯が別クラスタをつなぐ橋になる、という Granovetter の指摘のとおり）。
- **推奨:** 3つとも保存せず、エッジ重みと記録だけを持ち、密度・クラスタは分析時に計算する。

### 2.4 誰の視点の情報か（最重要）
- 「Aさんは犬が好き」は事実ではなく「誰かがそう記録した/そう推測した」情報。人間とAIエージェントの両方が書く前提なら、出典・記録者・日時・確度がないと、誤情報を消せず、AIの推測と本人の発言の区別もつかない。
- 「AさんとBさんは仲が良い」のような第三者間の関係を、自分の観測として記録するかどうかも決める必要がある（自分中心のエゴネットワークか、全体ネットワークか）。
- **推奨:** 値を直接ノードに書くのではなく、「主張（Fact/Observation）」として `出典・記録者(人/エージェント)・観測日時・有効期間・確度・本人申告/推測` を付けて積む。ノードの「現在の姿」はそこから導出する。

### 2.5 時間
- 関係も属性も変わる（転職、疎遠、引越し）。「ブラッシュアップを続ける」なら上書きではなく履歴が必要。
- **推奨:** 有効期間（いつからいつまで真か）と記録時刻を分けて持つ（bitemporal）。

### 2.6 ノードは人だけか
- 会社・コミュニティ・家族、そして「5人で会った飲み会」のような複数人のイベントは、人と人のエッジだけでは表現しきれない。
- **推奨:** Person 以外に Organization / Group / Event（Interaction）もノードとして持つ。

### 2.7 名寄せ（フィールド名より大きい揺れ）
- マスターが防ぐのはフィールド**名**の揺れ。実際にはそれ以上に「同一人物が別ノードになる」（"田中さん" と "田中太郎" と "t.tanaka@…"）と「値の揺れ」（"Google" / "グーグル" / "Google LLC"）が問題になる。
- **推奨:** 人物の別名・識別子を持つ仕組みと統合（マージ）操作を初期から設計に入れる。値の揺れは、選択肢型フィールドや参照型（会社は Organization ノードを参照）で抑える。

### 2.8 マスター運用
- 厳しすぎるとエージェントが書けず、緩すぎると揺れる。
- **推奨:** フィールド定義に `キー・表示名・型・別名(aliases)・適用対象・状態(提案/承認/廃止)` を持たせ、エージェントは未登録フィールドを「提案」として書け、人間が承認または既存フィールドへの統合を決める。別名で書かれたものは正規キーに自動変換。

## 3. リスク

### 3.1 プライバシー・法的（※法的判断は要確認、断定ではない）
- **本人の同意なく第三者の情報を記録するツール**であることが本質的なリスク。
- 個人情報保護法: 純粋に私的な利用は対象外だが、営業・採用などの**事業目的で使うと個人情報取扱事業者の義務がかかる**。特に要配慮個人情報（病歴・信条・犯罪歴など）は本人同意なしの取得が原則禁止。EU居住者が対象に入り事業利用ならGDPRも関係する。
- AIによる推測で生まれる属性（性格・健康状態・思想などの推定）は、本人が言っていない機微情報を作り出す。推測値は明示的に区別し、要配慮カテゴリは推測させない設計が望ましい。

### 3.2 外部AIへの送信
- エージェントが LLM API を使うと、第三者の個人情報を外部サービスに送ることになる。送信する範囲の最小化と、フィールドごとの「AIに渡してよいか」フラグを検討すべき。

### 3.3 セキュリティ
- 漏洩時の被害が非常に大きいデータ（人間関係の地図＋個人の詳細）。保存時暗号化、アクセス制御、ローカル優先の検討が必要。
- **プロンプトインジェクション:** メールやチャットから取り込んだ文章をコンテキストに保存し、それをエージェントが読むと、その文章中の指示に操られる危険がある。取り込んだ原文は「データ」として隔離して保存する。

### 3.4 削除
- 「この人の情報を全部消す」が、ノード・エッジ・主張・イベント参加・ログ・検索インデックスまで確実に効く設計にしておく必要がある。

### 3.5 倫理・社会的リスク
- 記録の存在や内容を本人が知った場合の関係悪化、操作的な利用（相手の弱点を記録して交渉に使う等）。ツールの用途をREADME等で明示しておくと良い。

## 4. 既存手法との比較

| 系統 | 例 | 本要求と重なる点 | 足りない点 |
|---|---|---|---|
| 個人向けCRM | Monica（OSS）, Clay, Dex, Folk | 人物ごとの情報・カスタムフィールド・リマインダ | 第三者間の関係やクラスタはほぼ扱わない。人物中心でグラフではない |
| 業務CRM | Salesforce, HubSpot | **管理者がカスタムフィールドを一元管理**（マスターの考え方そのもの） | 組織・商談中心。個人間の関係の強さは扱わない |
| ナレッジグラフ/オントロジー | Neo4j, Wikidata, schema.org `Person`, FOAF, vCard | プロパティグラフ構造。Wikidata は**プロパティを提案→承認で増やす**運用 | 個人的な人間関係用ではない。ただし語彙（フィールド名）は流用できる |
| ノートのグラフ | Obsidian, Logseq, Roam | 人物ページ＋リンク＋プロパティ | プロパティ揺れが実際に起きやすい。関係の強さの概念はない |
| **AIエージェント記憶** | **Zep / Graphiti**, Mem0（グラフメモリ）, Microsoft GraphRAG | 会話からエンティティと関係を抽出し**時間付きナレッジグラフ**に積む。GraphRAG はコミュニティ検出も行う | 汎用記憶であり人間関係に特化していない。フィールド定義のマスター管理や人間による編集は弱い |
| SNA分析 | NetworkX, Gephi | 強度・密度・クラスタの計算 | 記録・管理の機能はない（分析ライブラリとして使える） |

**差別化できる点:** ①フィールドマスター＋別名正規化による揺れ防止、②人間とエージェントが同じデータを共同編集できること（出典・確度付き）、③やり取り記録から関係の強さを導出すること。この3点の組み合わせは既存製品にはほぼない。

**注意点:** Graphiti（Zep）は「時間付きのエンティティ・関係グラフをエージェントが育てる」という点で本要求にかなり近い。データ設計で bitemporal なエッジやエピソード（出典）の持ち方を参考にする価値がある。ゼロから作るか一部を流用するかは、データ設計後に判断すればよい。

## 5. データ設計の叩き台（概念のみ・未確定）

検証結果を踏まえ、設計で扱う予定の概念:

- **Entity**: Person / Organization / Group（別名・識別子・マージ履歴を持つ）
- **Relationship**: 種類付き・向き付きのエッジ（同僚・友人・家族…は多重に持てる）、有効期間
- **Interaction**: 日時・参加者・チャネル・要約・原文への参照（強度算出の材料）
- **Fact（主張）**: 対象（Entity か Relationship）・フィールドキー・値・出典・記録者（人/エージェント）・確度・本人申告/推測・有効期間
- **FieldDefinition（マスター）**: キー・表示名・型・別名・適用対象・状態（提案/承認/廃止）・機微度・AI送信可否
- 強度・密度・クラスタは**派生値**（保存するならキャッシュ扱い）

## 6. 設計前に決めたいこと（推奨付き）

1. **利用者**: 自分だけ / 複数人で共有 → 推奨: まず「自分だけ」
2. **用途**: 私的 / 仕事も含む → 法的義務が変わるため要確認
3. **保存場所**: ローカル / クラウド → 推奨: 「ローカル」（漏洩リスクと外部送信を抑える）
4. **関係の強さ**: 手入力 / やり取りから算出 / 両方 → 推奨: 「両方」

**回答（2026-10-12）:** 1. 自分用 / 2. 仕事も含む / 3. VPS に置き、AIエージェントやスマホから参照 / 4. 両方。基本はエージェントが操作・設定し、人は参照が中心。→ [データモデル](data-model.md) に反映。
